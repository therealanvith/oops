# Risks, Mitigations & Key Assumptions

## 1. Technical & Project Risks with Mitigations

| Risk ID | Description & Potential Impact | Likelihood / Severity | Mitigation Strategy |
| :--- | :--- | :---: | :--- |
| **R-01** | **Accidental Domain Contamination**: A developer imports `@Entity`, `@Transactional`, or Spring beans into `com.servicedesk.domain`. | Medium / **Critical** | Automated ArchUnit test (`DomainIsolationTest`) runs on every commit and CI build, failing immediately upon any domain import violation. |
| **R-02** | **Frontend-Backend Integration Lag**: Frontend development gets blocked waiting for backend REST endpoints to be fully implemented. | High / High | Fixed API contract specification (`docs/api-spec.md`) and mock JSON responses allow Owner 3 to develop Next.js components in parallel without blocking. |
| **R-03** | **Time/Clock Flakiness in Tests**: Tests evaluating SLA breach deadlines or paused durations become flaky due to system clock drift or execution lag. | Medium / High | Strict adherence to injecting a mockable `java.time.Clock` into domain entities and services, avoiding `Instant.now()` or `System.currentTimeMillis()`. |
| **R-04** | **Scope Creep on Intelligent Features**: Attempting to integrate heavy external AI/LLM models causing latency, dependency bloat, or API cost/rate-limiting issues. | High / Medium | Scope is strictly locked to local, deterministic algorithms (tokenized Jaccard similarity and rule-based keyword classification). Marked any LLM features as purely COULD. |
| **R-05** | **Tight Deadline (12 Working Days)**: Delays in one area jeopardizing the submission on 22 Nov 2026. | High / High | Rigid MoSCoW prioritization: MUST scope covers all evaluation criteria. Non-critical enhancements (attachments, charts) are deferred until the working MVP demo is verified. |

## 2. Assumptions to Confirm with Project Lead / Evaluator

Please review and confirm the following design decisions:

1. **Authentication Mode**:
   - *Assumption*: We will use standard JWT bearer tokens generated by Spring Security with pre-seeded demo user accounts (`employee1`, `tech_network`, `tech_hardware`, `admin`).
   - *Confirmation Needed*: Is lightweight in-memory/database authentication sufficient, or is university LDAP/SSO integration expected? *(Recommended: DB/JWT is standard for course projects).*
2. **Notification Channels**:
   - *Assumption*: To avoid external SMTP relay configuration during evaluation, the email notification channel will log formatted emails to the server console and maintain an in-memory/database outbound inbox visible via an API endpoint.
   - *Confirmation Needed*: Is console/logger simulation acceptable for the Email channel, paired with live In-App notifications in the web UI?
3. **Similarity Detection Algorithm**:
   - *Assumption*: Token-based Jaccard similarity ($|A \cap B| / |A \cup B|$) on normalized lowercase text is sufficient to satisfy the "Intelligent Incident Similarity" grading requirement without external Python/ML dependencies.
   - *Confirmation Needed*: Does this meet the course expectation for intelligent algorithms within pure OOP?
4. **SLA Clock Precision**:
   - *Assumption*: SLA countdowns are evaluated on request and via a periodic background task running every 60 seconds.
   - *Confirmation Needed*: Is a 60-second polling resolution sufficient for demo purposes (with manual trigger `/api/v1/admin/sla/evaluate` available for instant demo verification)?
